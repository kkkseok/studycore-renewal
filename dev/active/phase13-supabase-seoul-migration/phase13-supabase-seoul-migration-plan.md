## 기술 결정

### 1. 데이터 이전: 운영 DB 덤프 → 복원

- `supabase/migrations/`를 새로 실행하지 않는다. 운영과 어긋나 있어(054 미반영) 덤프가 정본이다.
- 도구: Postgres 17 클라이언트(`pg_dump`/`psql`). 서버가 17.6이라 클라이언트도 17 이상이어야 한다. Docker가 없어 `supabase db dump`(Docker 필요)는 쓰지 않는다.
- 대상:
  - `public` 스키마: 구조 + 데이터 (테이블, RLS 정책, 함수, 트리거, 권한)
  - `auth` 스키마: **데이터만** (구조는 Supabase가 관리). 사용자 ID·비밀번호 해시·identity가 유지되어야 `profiles` FK와 카카오 계정 연결이 그대로 동작
  - `auth.users`의 `on_auth_user_created` 트리거: public 쪽 함수와 함께 복원되는지 확인, 누락 시 수동 생성
  - `storage.buckets` 행과 storage 정책 32개
- `auth.sessions`·`auth.refresh_tokens`는 옮기지 않는다 (새 프로젝트는 JWT 키가 달라 어차피 무효).
- 복원은 공식 절차와 같은 형태로 한다: `psql --single-transaction --variable ON_ERROR_STOP=1`, 데이터 적재 전 `SET session_replication_role = replica`(트리거 비활성). 덤프는 `--no-owner`로 만들어 `supabase_admin` 소유권 오류를 피한다.
- 커스텀 role이 없어 role 덤프는 생략한다.
- 접속은 세션 풀러(포트 5432) 연결 문자열. 덤프 파일에 `COPY auth.users`·`auth.identities`·`storage.buckets`가 들어 있는지 리허설에서 확인한다.
- 연결 문자열의 DB 비밀번호는 환경변수로만 전달하고 명령·로그에 값을 남기지 않는다.

### 2. Storage: 파일 복사 스크립트

- `storage.objects` 행은 덤프로 옮기지 않는다 (행만 있고 파일이 없는 상태가 됨).
- 일회성 Node 스크립트로 기존 프로젝트에서 내려받아 새 프로젝트에 같은 버킷·같은 경로로 올린다. 164개 / 69MB.
- 경로가 같으므로 공개 URL은 프로젝트 ref 부분만 달라진다 → 아래 3번의 단순 치환이 성립.
- 스크립트는 scratchpad에 두고 저장소에 커밋하지 않는다.

### 3. 본문 주소 치환 (새 DB에서만)

- 대상 5개 테이블(question_answers 27, questions 26, notices 13, spaces 10, guide_sections 2)에서 `wshmxjctdwhasxhjxlxm` → 새 ref.
- 컬럼 단위 `replace()` UPDATE. 실행 전 대상 컬럼을 테이블별로 확정하고, 실행 후 완료 기준 2번 스캔으로 0건 확인.
- 기존 DB는 수정하지 않는다.

### 4. Auth 설정 수동 이전

덤프에 포함되지 않는 항목. 기존 대시보드 값을 화면으로 확인해 새 프로젝트에 동일하게 입력한다.

- Site URL, Redirect URL 허용 목록
- 카카오 provider (Client ID / Secret — 값은 사용자가 직접 입력)
- 가입·세션·rate limit 등은 context "기존 Auth 설정" 표대로 입력 (대부분 기본값)
- 카카오 개발자 콘솔 Redirect URI에 `https://<새 ref>.supabase.co/auth/v1/callback` **추가** (기존 것은 삭제하지 않음 → 롤백 가능)

### 5. Edge Function

- 4개 함수를 새 프로젝트에 배포, 시크릿 5개 등록 (값은 사용자가 입력하거나 기존 값을 직접 옮김).
- 배포 명령: `npx supabase@latest functions deploy --use-api --remote=<새 ref>` (Docker 불필요, CLI 3.2.0 도움말로 확인). `supabase login`은 사용자가 직접.
- 기존 함수의 JWT 검증 설정(`verify_jwt`)을 기존 프로젝트와 같게 맞춘다. 기존 값은 배포 전 대시보드에서 확인.
- `SUPABASE_URL`·`SUPABASE_SERVICE_ROLE_KEY`는 플랫폼이 자동 주입하므로 따로 넣지 않는다.

### 6. 전환 방식: 리허설 1회 + 새벽 본 전환

데이터가 작아(23MB) 증분 동기화 대신 **본 전환 때 데이터를 통째로 다시 덤프·복원**한다.

- **리허설 (낮, 운영 영향 없음)**: 새 프로젝트에 전체 이전 → `.env.local`을 새 프로젝트로 바꿔 로컬 E2E·수동 검증. 소요 시간 측정.
- **본 전환 (새벽)** — 2026-11-23 리허설 결과로 수정: 쓰기 동결 대신 **무중단 + 사후 대조** 방식.
  1. 기존 DB 기준값 기록 (`counts.sql` 결과 = 스냅샷 A)
  2. 최종 덤프 → 새 DB의 `public`·`auth` 데이터를 비우고 복원, 주소 치환, Storage 차분 복사
  3. Vercel 환경변수 3개 교체 + `vercel.json`에 `"regions": ["icn1"]` 추가 → 한 번의 운영 배포
  4. `studycore-dashboard`의 `web/config.js` URL·anon 키 교체 배포
  5. 완료 기준 1~8 확인
  6. **기존 DB 재대조** (스냅샷 B): A와 다르면 1~3 사이에 기존 DB로 들어온 쓰기가 있다는 뜻 → 해당 행을 새 DB로 수동 반영
  7. 기존 프로젝트 API 차단 (아래 7번)
  8. Supabase MCP 커넥터와 광고 분석 루틴 2개를 새 프로젝트로 전환
- 동결을 하지 않는 이유: 동결하면 그 시간의 상담 신청이 오류로 실패해 리드를 잃는다. 동결하지 않으면 그 시간의 신청은 기존 DB에 정상 저장되고(알림도 발송됨) 6단계에서 옮기면 된다. 리허설 실측 소요: 덤프 72초, 복원 9초, Storage 전체 복사 87초(본 전환은 차분만), 주소 치환 수 초.

### 7. 구버전 클라이언트의 이중 쓰기 방지

전환 시점에 열려 있던 탭·PWA 캐시는 기존 프로젝트 주소가 박힌 번들로 계속 동작한다. 전환 검증이 끝난 뒤 기존 프로젝트의 API를 막으면 이런 클라이언트의 요청은 조용히 갈라지지 않고 **오류로 실패**하며, 새로고침하면 새 번들을 받는다.

- 방법 (2026-11-23 새 프로젝트에서 시험):
  - 차단: `ALTER DATABASE postgres SET default_transaction_read_only = true;` 후 API role 연결 종료(`pg_terminate_backend`, usename `authenticator` 등). 설정만으로는 기존 연결에 적용되지 않았고(쓰기 204), 연결을 끊은 뒤에는 **읽기·쓰기 모두 503**(PGRST002, 스키마 캐시 로드 실패)이 됐다. 즉 "쓰기만 차단"이 아니라 API 전체 차단이다.
  - 해제: `ALTER DATABASE postgres RESET default_transaction_read_only;` + `NOTIFY pgrst, 'reload schema'` → 약 5초 뒤 200 복구 확인. 해제 명령은 세션이 읽기 전용이라 `PGOPTIONS='-c default_transaction_read_only=off'`로 접속해야 한다.
- 전체 차단이므로 **전환 검증이 끝난 뒤에만** 건다. 전환 도중에 걸면 사이트가 DB를 못 읽는다.
- 상담 신청·랜딩 리드는 서버 경유라 재배포 즉시 새 DB로 간다.

### 8. 롤백

| 시점 | 방법 |
|------|------|
| 본 전환 중 검증 실패 | Vercel 이전 배포로 Instant Rollback (환경변수·리전이 빌드에 묶여 있어 함께 복귀) → 대시보드 `config.js` 되돌림 → (이미 걸었다면) 기존 프로젝트 API 차단 해제 |
| 전환 후 관찰 기간 | 위와 같음 + 그 사이 새 DB에 쌓인 데이터를 기존 DB로 수동 반영 필요. 시간이 지날수록 비용이 커지므로 전환 당일 검증을 엄격히 |
| 기존 프로젝트 삭제 후 | 롤백 불가. 삭제 전 최종 덤프를 로컬에 보관 |

### 9. 기존 프로젝트 삭제 조건

모두 충족 시 사용자 최종 승인 후 삭제:

- 전환 후 1~2주 경과, 완료 기준 9·10 유지
- 기존 프로젝트 API 요청 로그에 의미 있는 트래픽 없음
- 최종 덤프 로컬 보관 확인
- 카카오 콘솔의 기존 Redirect URI 제거, 로컬 덤프·스크립트 정리는 삭제 후 진행
